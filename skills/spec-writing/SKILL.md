# 技术方案写作规范

目标读者是**评审人**（熟悉业务但不一定熟这块代码）。让评审者 3 分钟内看懂：改什么、怎么改、为什么、风险、要拍板什么。

## 写作总原则

1. **先说人话，再说细节**。每个大节先给结论，再铺背景
2. **多用判断句**："我建议 X 不选 Y，因为 …"；避免"可能需要考虑"
3. **章节有信息增量才写**。模板里的小节是上限不是下限，无内容整节省略
4. **不写施工单**。方案是给人读的判断材料，不是改动清单

两条格式硬底线：
- 关键决策每条标题**以问号结尾**
- 验收标准用 `### 场景 N` + "给定/当/则"，不用 `- [ ]` checkbox

## 方案模板

```markdown
# <方案标题>

## 一页结论

约 200-300 字，回答 5 件事：
1. 要解决什么
2. 推荐怎么做
3. 为什么这样做
4. 最需要拍板的点
5. 风险结论

不放文件路径、函数签名等细节。

## 背景与目标

- 问题/需求：2-3 句
- 目标："完成后应该能 XXX"
- 非目标：有真实边界意义的才写

## 现状分析

只答：当前逻辑在哪一层 / 为什么不满足 / 改动落哪一层 / 必须沿用的约束。引用代码位置最多 2-4 个。

## 方案设计

### 方案概述

1. 先描述改动前的请求/数据流，标出"本次要动第 X 步"
2. 按流程顺序讲改动，每处说"原本怎样 → 改完怎样"
3. 多路分支用表格对比
4. 容易踩的坑单独一段

### 方案对比

仅在确有 trade-off 时出现。每个方案写：核心思路 / 优缺点 / 适用前提。结尾明确推荐项和原因。

### 详细设计

以下小节按需保留，无信息增量的省略：

- **模块与职责变更**：改动落哪些模块，职责怎么变
- **数据与状态**：涉 DB/缓存/配置才写。涉 DB 必须用 `mcp__postgres-db__query` 实查 schema，产出完整 DDL、破坏性标注、大表锁风险、回滚 SQL
- **错误处理策略**：降级还是报错、是否重试
- **并发/异步模型**：有特殊点才展开
- **API/接口变化**：公开 API / HTTP / RPC
- **核心流程**：Mermaid 或简明步骤
- **文件变更清单**：表格说"为什么改这个文件"

## 关键决策

只列需要外部拍板或事后可能被质疑的决策，2-5 条。

每条标题以问号结尾。需外部确认的独立写 `**需 PM 在上线前确认：<具体问题>**`。

## 风险与边界

- **已知风险**：表格（风险/影响/缓解）
- **边界场景**：对本次设计有影响的才列
- **兼容性**：公开 API 是否破坏、旧数据/缓存是否受影响

## 验收标准

### 业务场景验收

每个场景独立 `###` 标题，内部用"给定/当/则"三段式。至少覆盖：
1. 核心功能路径
2. 边界（空值/禁用/缺失）
3. 兼容/降级（没用新功能时行为不变）

### 工程质量基线

一段清单：编译/lint/测试全绿、新增公开 API 有文档、关键路径有日志。

## 工作量估算

简要拆分即可。

## 待确认

仅在确有未决事项时出现，≤3 条。
```

## 写作纪律

1. 每句话服务于本次需求，不塞"最佳实践"科普
2. 文件路径要真实，从代码库中确认后再写
3. 数据模型写具体字段，API 写具体结构
4. 不确定的写"待确认"，不用"可能""大概"糊弄
5. 多方案对比时每个方案写完整设计，不能"类似方案 A 但是..."
6. 数据库变更必须基于实查，MCP 查不通标"待确认：需人工查询 schema"
