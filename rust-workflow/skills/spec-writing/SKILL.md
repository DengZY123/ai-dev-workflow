# 技术方案写作规范

目标读者是**评审人**（熟悉业务但不一定熟这块代码）。一切规则服务于一个目标：让评审者 3 分钟内看懂改什么、怎么改、为什么、风险、要拍板什么。

## 写作总原则

1. **先说人话，再说细节**。每个大节先给结论/建议，再铺背景；不要上来就堆文件路径、行号、签名
2. **多用判断句**："我建议 / 不建议 / 这里选 A 不选 B，因为 …"；避免"可能需要考虑"这种骑墙
3. **章节有信息增量才写**。下面模板里的所有小节都是**上限，不是下限**。无内容的整节省略或一句"无"带过
4. **不技术炫耀**。扫到的细节不全写；与本次决策无关的现状删掉
5. **不写施工单**。方案是给人读的判断材料，不是给 AI 读的改动清单；不要把"在 X 文件加 Y 字段"当方案主体

**两条最容易回退的硬底线**，贯穿全文：

- 关键决策每条标题**以问号结尾**（不是问句 = 不是决策）
- 验收标准**严禁 `- [ ]` checkbox 语法**（业务场景用 `### 场景 N` + "给定 / 当 / 则"）

## 方案模板

```markdown
# <方案标题>

## 一页结论

约 200–300 字，固定回答 5 件事，像跟同事解释：

1. 这次要解决什么
2. 推荐怎么做
3. 为什么这样做
4. 最需要拍板的点
5. 风险结论

**禁止**：文件路径、行号、缓存 key、函数签名、类型签名。

## 背景与目标

- 问题/需求：2–3 句
- 目标："完成后应该能 XXX"
- 非目标：有真实边界意义的才写，没有就省略

## 现状分析

只答四件事，不写成源码导览：当前逻辑在哪一层 / 为什么不满足 / 改动落哪一层 / 有哪些约束必须沿用。引用代码位置**最多 2–4 个**。

## 方案设计

### 方案概述

**硬性结构**：

1. 第一段必须是"改动前的请求/数据流"完整伪步骤，末尾标"本次要动第 X 步"
2. 按流程顺序讲改动，每处说"原本怎样 → 改完怎样"
3. 多路分支（三态 / 降级 / 容错）用表格或小标题对比
4. 容易踩的坑单独一段（如有）

**硬性禁止**：

- 以 "1. X 扩字段 / 2. Y 加参" 文件清单开头
- 第一段就列改动点，没有流程铺垫
- 用类型签名 / SQL 片段代替人话
- 1–2 段草草带过

**反面示例**（施工单风格，见到重写）：

> 三步改动:
> 1. `ApiKeyInfo` 扩字段 `permissions`
> 2. `resolve_channels` 新增入参
> 3. `clear_user_channel_cache` 扩展 SCAN

**正面示例**：

> 代理接到请求现在流程是：
>
> ```
> 1. 查 token 得 ApiKeyInfo
> 2. 调 resolve_channels 按 user_discount_tier 过滤 → 权重洗牌 → 缓存 5 分钟
> 3. 选一个转发
> ```
>
> 本次要动第 1、2 步。
>
> **第 1 步：查库多取一列 `permissions`**。ApiKeyInfo 加可选字段，30s 缓存照旧，旧缓存没字段也不炸。
>
> **第 2 步：调 resolve_channels 前看 key 的 `permissions.channels[model]`**：
>
> | 配置 | 做什么 |
> |---|---|
> | null 或没当前 model | 当没看见，走老流程 |
> | 非空数组 `[0.6]` | 在用户级过滤后再留下 `discount_rate ∈ 数组` 的渠道 |
> | 空数组 `[]` | 这把 key 禁用该模型，直接返回"无可用渠道" |
>
> **两个坑**：
> - 脏数据：Dashboard 可能写非法 permissions。warn + 当作没配，不甩 500
> - model 降级：两次调用要分别跑白名单判断，不能把第一次 filter 带到第二次

### 方案对比

**仅在确有 trade-off 时出现**。每个方案写：核心思路 / 优点 / 缺点 / 适用前提。结尾明确"**本次推荐 X，原因 …**"。没有真实取舍就不写这节。

### 详细设计

以下小节**按需保留**，无信息增量的整节省略或一句"无"：

- **模块与职责变更**：改动落哪些 crate / 模块，职责怎么变
- **数据与状态**：涉 DB / 缓存 / 配置 / 内存状态才写。**涉 DB 必须用 `mcp__postgres-db__query` 实查 schema**（见下方）
- **错误处理策略**：只写有决策意义的（降级还是报错、是否 fallback、是否重试）
- **并发 / 异步模型**：有特殊点才展开（新任务、共享状态、阻塞需 `spawn_blocking`）
- **API / 接口变化**：公开 API / HTTP / RPC；内部小改不写细
- **核心流程**：Mermaid 或简明步骤
- **文件变更清单**：表格说"**为什么改这个文件**"，不是"加了几个字段"

**DB 实查要点**（仅涉 DB 时）：

1. 字段：`SELECT column_name, data_type, is_nullable, column_default FROM information_schema.columns WHERE table_name = '<t>'`
2. 索引：`SELECT indexname, indexdef FROM pg_indexes WHERE tablename = '<t>'`
3. 外键：`SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = '<t>'::regclass`
4. 大表行数：`SELECT reltuples::bigint FROM pg_class WHERE relname = '<t>'`

产出完整 DDL、破坏性标注、大表（>100 万行）锁风险与 `CREATE INDEX CONCURRENTLY` 建议、回滚 SQL；MCP 查不通标"待确认：需人工查询 schema"。

## 关键决策

**只列需要外部拍板或事后可能被质疑的决策**，2–5 条。

**收录**：需 PM / 架构师确认的语义与产品取舍 / 事后可能被质疑"为什么不走 X" 的选择 / 有明显 trade-off 的选择。

**不收录**：命名、类型、常量、实现位置选择 / 行业通识（`Option`、`serde(default)`、`Arc`）/ 方案其他章节已讲过的。

**硬性格式**：

1. **标题必须以问号结尾**
   - ❌ "决策 1：缓存按 api_key_id 维度"
   - ✅ "决策 1：缓存按 api_key_id 维度，还是每次查 DB？"
2. 需外部确认就独立一行写 `**需 PM 在上线前确认：<具体问题>**`，不藏括号
3. 决策附带的外部确认写在本节；**不属于任何决策**的独立未决项才放顶层 `## 待确认`

**正面示例**：

> **决策 1：密钥级白名单相对用户级是"收窄"还是"覆盖"？**
>
> 答：收窄（SQL 里用 AND）。
>
> 理由：用户级白名单是账户授权边界。若"覆盖"语义，key 配 `[0.1]` 就能用 0.1 折渠道，等于 key 级越权。白名单语义下"优先级更高"和"收窄"不冲突。
>
> **需 PM 在上线前确认**：需求原文"密钥级优先级最高"的实际期望是收窄还是覆盖。若是后者，SQL 和测试要翻一遍。

## 风险与边界

### 已知风险

表格：风险 / 影响 / 缓解。只写真实风险：兼容性、数据迁移、缓存一致性、编译时间、二进制体积、MSRV、unsafe invariant、性能/容量。

### 边界场景

只列对本次设计有影响的边界情况，不穷举可能输入。

### 兼容性

公开 API 是否破坏（SemVer / MSRV）、旧数据/缓存/行为是否受影响、平滑兼容路径。

## 验收标准

分两段：**业务场景验收** + **工程质量基线**。

**硬性禁止**：

- `- [ ]` checkbox 语法
- "行为级 / 测试级 / 工具链级 / 可观测性级 / 文档级" 前缀或分类
- 英文 snake_case 测试函数名作场景名
- "新增逻辑必须有单元/集成测试"这类测试策略陈述
- 把"关键路径有 tracing / API 有 `///`"写进业务场景
- "功能正常" / "覆盖全部场景" 等模糊条目

### 业务场景验收

每个场景独立 `###` 三级标题（中文短句），内部用"**给定 / 当 / 则**"三段式。按 Size 自适应，至少覆盖前 3 类：

1. 核心功能路径（happy path）
2. 边界（空值 / 禁用 / 缺失字段）
3. 兼容 / 降级（没用新功能时行为不变）
4. 异常 / 脏数据 —— 涉及才写
5. 副作用（缓存、日志、清理） —— 涉及才写

**正面示例**：

> ### 场景 1：密钥有白名单时只命中白名单内的渠道
>
> - **给定**：user A 的 user_discount_tier 允许 claude_code 走 {0.1, 0.6}；key K1 配 `permissions.channels.claude_code = [0.6]`
> - **当**：用 K1 发 10 次 claude_code 请求
> - **则**：10 次全部转发到 discount_rate = 0.6 的渠道；tracing 日志 `allowed_discounts = [0.6]`
>
> ### 场景 2：密钥无配置时行为与上线前一致
>
> - **给定**：同 user 另一把 key K2，`permissions = null`
> - **当**：用 K2 发请求
> - **则**：候选渠道分布与 main 分支一致；缓存 key 前缀不含 api_key_id

### 工程质量基线

一段清单，不拆到场景里重复：

- `cargo fmt --check` / `cargo clippy --all-targets -- -D warnings` / `cargo test` 全绿
- 新增公开 API 有 `///` 文档
- 关键路径有 `tracing` 日志（含 request_id 等核心字段）
- 新增 `unsafe` 块有 Safety 注释 + 测试策略
- HTTP 接口按项目约定更新文档

## 工作量估算

简要拆分，不像项目排期表。

## 待确认

**仅在确有未决事项时出现**，≤3 条。只放不属于任何决策的独立问题；决策附带的外部确认已在关键决策内写明。
```
